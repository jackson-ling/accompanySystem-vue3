# 陪诊预约项目开发要求

## AI 生成代码规约

回答规约：必须使用中文与用户交互

修复代码要求：AI必须认真审查代码并修复代码错误，前提是不能影响已有代码的功能和样式，考虑文件之间的关联，并且修复过程不允许出现新的错误，若出现，应该重新修复，直到没有任何报错

新增代码要求

- 首先检测新增代码的文件是否有没有被引用的代码，删除，前提是不能影响已有代码的样式和功能
- 新增代码不能影响已有代码的样式和功能，代码应该符合企业开发规范，统一代码风格，不要出现冗余代码，能复用的需要抽取出来，提高可维护性和可扩展性，同时检查代码文件中没有用的代码，应当删除，并且不能影响项目的功能和样式
- 新增代码的样式不能出现被遮挡，错乱，与项目样式不适配的情况，生代码后应该先自测，如果出现错误，应及时修复，直到没有任何报错
- 新增代码完成后，再次检测新增代码的文件是否有没有被引用的代码，删除，前提是不能影响已有代码的样式和功能

文件规范：所有代码文件要求符合开发命名规范，并且需要规范的放在文件夹中，是否存放在文件夹中根据实际情况而定，参考企业真实前端开发的代码规范

样式要求：所有样式和用户需求首先应该满足移动web的设计，在此基础上符合web端，二者的样式必须保持一直且不可以相互影响

自动化自测与预评估：代码生成后，AI应首先执行自测，检查交互逻辑、样式、API及数据库交互等是否符合预期。这一过程帮助确保用户体验顺畅，避免基础问题出现在用户测试时。

问题自动定位与修复：AI应能自动检测出样式、交互等方面的问题，并在生成代码后主动修复，如有潜在问题，提供修复方案，减少用户发现问题的时间。

质量审查与反馈：AI需要对生成代码进行严格审查，确保功能的正确性和一致性，并在发现问题时及时修复。

持续优化：AI通过反馈机制，对交互、样式等细节进行持续优化，确保生成的代码始终符合项目需求并达到预期的质量标准。

## 开发流程

1. **界面开发：**
   - 按照后端要求逐一开发前端界面，确保交互逻辑和样式与移动端和 PC 端的要求兼容。
   - 新增组件和界面必须遵循移动 Web 开发风格，不能因为一端的样式而影响另一端。

2. **API 请求：**
   - 开发完成界面后，审阅所有前端代码，根据前端来生成接口文档，并根据用户的要求做出相关调整，待用户确认无误后，根据接口文档将所有API请求逻辑写入前端代码，并确保数据处理的合理性。
   - 请求路径需遵循 `/api/请求接口` 格式，并通过 `vite.config.ts` 进行路径重写，将请求代理到后端的 8080 端口。
   - 所有 API 请求必须分模块进行分类，并确保每个 API 文件命名和接口路径清晰。

3. **数据库设计与接口：**
   - 根据接口文档和用户需求设计数据库表，并实现相应的接口。
   - 所有接口文档需明确描述参数、返回格式以及错误处理。

## API 接口文档规范

一旦前端界面达到预期效果，AI 将根据前端组件的实际实现自动生成相应的 API 接口文档。

API 接口文档需要遵循以下格式：

接口路径： /api/{模块}/{接口}

请求方法： GET, POST, PUT, DELETE

请求参数： 明确每个请求所需的参数类型、是否必需、默认值等。

返回结果： 详细描述返回的数据格式、字段类型及说明。

错误处理： 统一的错误码及其对应的错误信息。

接口示例： 每个接口提供一个请求示例和一个响应示例。

API文档应包括API的详细描述、请求与响应的格式（如JSON）、每个接口的功能、权限要求以及与数据库表的交互方式。接口文档应尽量清晰，以便AI根据文档精确地生成数据库设计。

## 数据库设计应规范

在前端完成后，AI 将根据前端功能需求和 API 接口文档自动生成数据库设计。

表结构设计：

确定每个表的字段，包括字段名、数据类型、最大长度、是否允许为空等。对于数字、时间等特殊类型的字段，需要详细说明格式。

AI应根据API接口中涉及的数据交互，自动推导出字段的类型。例如，用户信息表可能需要存储邮箱（string），密码（hash），而订单表需要存储订单金额（decimal）、时间戳（datetime）等。

关系设计：

确定表与表之间的关系，如一对多、多对多等。AI可以分析API文档中的接口设计来识别这些关系，并通过外键约束来体现。

例如，如果用户表和订单表是“一对多”关系，AI应识别并设计用户表与订单表之间的外键关联。

字段说明：

每个字段需要明确其含义、取值范围和默认值。对于某些特殊字段（如日期字段、状态字段等），需要明确其业务含义及约束。

AI可以自动生成字段说明，比如在用户表中的“status”字段可以注明“用户状态，取值范围：‘active’, ‘inactive’, ‘suspended’，默认值为‘active’”。

3. 优化建议

支持动态调整：

随着需求的变化，AI应支持动态调整数据库设计。例如，增加或删除字段、修改字段类型、调整表的关系等，保证数据库设计与实际需求的同步。

## 开发规约

1. **API 请求：**
   - 所有 API 请求文件需存放在 `src/api/` 目录下，按功能模块分类：

     ```
     src/api/
     ├── auth.ts       # 认证相关 API
     ├── user.ts       # 用户管理 API
     ├── product.ts    # 商品相关 API
     └── appointment.ts # 预约相关 API
     ```

   - API 请求的命名方式统一，采用小写字母和下划线（如 `get_user_info`）。
   - 在 `vite.config.ts` 中配置代理，确保请求路径正确：
     ```ts
     export default defineConfig({
       server: {
         proxy: {
           '/api': {
             target: 'http://localhost:8080',
             changeOrigin: true,
             rewrite: (path) => path.replace(/^\/api/, ''),
           },
         },
       },
     })
     ```

2. **图片处理：**
   - 组件中使用的图片需从网络（如 Unsplash）获取并下载到 `public` 目录中。
   - 图片命名需清晰，确保易于管理。

3. **路径重写：**
   - 配置 `vite.config.ts`，将所有 `/api/` 请求路径代理到后端的 8080 端口。

## 最佳实践

1. **Vue3 Composition API：**
   - 使用 `setup()` 函数处理组件逻辑，利用 `ref` 和 `reactive` 管理响应式状态。
   - 使用 `computed()` 实现计算属性，使用 `watch` 处理副作用。
   - 使用 `onMounted`、`onUpdated` 等生命周期钩子。
2. **TypeScript 集成：**
   - 实现组件类型定义，使用 `props` 和 `emit` 定义，确保类型安全。
   - 为每个 API 请求定义相应的类型，避免类型错误。

3. **Pinia 状态管理：**
   - 使用 Pinia 进行状态管理，确保状态管理模块化，避免出现全局状态污染。

4. **性能优化：**
   - 使用懒加载组件，避免一次性加载过多组件，提升性能。
   - 避免不必要的 `watcher` 和 `computed`，减少不必要的渲染。

## 附加建议

1. 明确的错误处理和异常管理：

提示和回退机制：用户界面上应该有适当的错误提示和回退方案，避免用户在遇到异常时无法理解发生了什么。

2. UI/UX 优化：

界面一致性：确保在移动端和 PC 端的所有组件样式和交互逻辑完全一致，避免由于界面在不同设备上的差异导致用户体验不一致的问题。可以考虑使用媒体查询来适配不同设备，或者使用响应式布局。

用户体验增强：在界面交互设计中引入更多细节，如按钮的点击反馈、加载状态、错误提示、成功提示等，增强用户操作的流畅性。

3. 项目架构的优化：

模块化和解耦：确保所有组件和服务的代码都做到模块化，避免逻辑和数据的耦合。比如，对于一些常用的组件，可以提取到 components/UI 中，对于一些公共的 API 请求逻辑，可以集中管理。

状态管理与数据流：在 Pinia 状态管理中，可以考虑使用 getters 和 actions 来处理复杂的状态变更逻辑，避免在组件中直接修改状态，保持数据流的清晰。

4. 开发流程中的代码规范：

代码风格一致性：确保整个团队遵循统一的代码风格，如 ESLint 和 Prettier 配置，减少因代码风格不同而带来的代码审查成本。
